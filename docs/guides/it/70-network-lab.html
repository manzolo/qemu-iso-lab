Network lab: pfSense, Pi-hole e Lubuntu

Laboratorio riproducibile di manzolo/qemu-iso-lab · profili pfsense-lab, pihole-lab, lubuntu22-lab · segmento lab-lan, dominio qlan · porting del network lab di kvm-lab su QEMU puro, con la strada libvirt tramite vmctl export-libvirt

Tre macchine virtuali ricreano una piccola rete aziendale su un segmento isolato: un firewall/router che fa NAT verso Internet, un resolver DNS con filtro pubblicità che distribuisce anche gli indirizzi via DHCP, e un client desktop. Tutto si installa da zero senza interazione (vmctl lab install) e si può distruggere e ricreare in una mezz'ora. La differenza rispetto a kvm-lab è dove sta l'host: su QEMU puro il segmento è un socket multicast fra le VM e l'host non ha un indirizzo sulla LAN, quindi entra dal lato WAN del firewall attraverso i port forward; dopo l'export in libvirt il segmento diventa la rete lab-lan e l'host torna a essere .254, come prima.

1. Schema della rete (QEMU puro)

2. I tre componenti

pfSense · firewall e gateway · profilo pfsense-lab

FreeBSD, pfSense CE 2.7.2, ZFS, BIOS, console seriale · install scriptata di bsdinstall, config.xml generato da vmctl

  • NAT: tutto ciò che esce da lab-lan viene mascherato con l'IP WAN preso dallo slirp di QEMU.
  • Regole LAN "allow LAN to any" (IPv4 e IPv6); regole WAN che permettono GUI (80) e SSH (22) dal lato WAN, cioè dall'host.
  • Port forward NAT: 8081 → Pi-hole :80, 2238 → Pi-hole :22, 2239 → Lubuntu :22.
  • DHCP LAN disabilitato: lo fa Pi-hole. Unbound attivo; DNS di sistema .10.
  • GUI in HTTP su http://127.0.0.1:8080/, utenti admin e quello del profilo (stessa password, hash bcrypt); chiave SSH del progetto già nei due account.

Pi-hole · DNS e DHCP · profilo pihole-lab

Ubuntu Server 22.04.5 (autoinstall) + Pi-hole v6 dall'installer ufficiale con pihole.toml pre-compilato

  • Resolver per tutta la LAN con blocklist StevenBlack.
  • Upstream OpenDNS 208.67.222.222 e .220.220, raggiunti attraverso pfSense.
  • Record locali generati: il router e ogni membro del lab (firewall.qlan, pi-hole.qlan, lubuntu.qlan), più quelli in network_lab.hosts; CNAME pfsense.qlan.
  • DHCP per gli ospiti: pool .150–.199, lease 24 h, gateway .1, DNS .10, dominio qlan.
  • GUI su http://127.0.0.1:8081/admin/ (attraverso il router), password network_lab.password.

Lubuntu · client · profilo lubuntu22-lab

Ubuntu Server 22.04.5 + lubuntu-desktop, LXQt, autologin SDDM

  • IP statico .100, gateway .1, DNS .10: la postazione utente.
  • NIC agganciata dal MAC nel netplan (match + set-name), stesso slot e stesso MAC in fase install e runtime.
  • Cartella shared/ dell'host su /mnt/shared (virtiofs), link ~/shared e sul desktop.
  • systemd-networkd-wait-online disabilitato: con renderer NetworkManager bloccava ogni boot per 120 s.

Host · dove si comanda

QEMU puro: 127.0.0.1 + forward · libvirt: 192.168.0.254 sul bridge virbr-lab

  • vmctl lab up/down/status/check, vmctl shell <vm>, vmctl console <vm> per la seriale, vmctl attach <vm> per lo schermo.
  • I forward sono nel profilo del router (networks[].hostfwd) e nelle regole NAT del config.xml: vmctl lab plan verifica che coincidano.
  • Dopo vmctl export-libvirt l'host sta sulla LAN e tutto è raggiungibile sugli IP veri.
  • In vmtui la riga "Network Lab" del dashboard raccoglie le stesse azioni (plan, install, install + export, up, down, check, export, unexport, round trip, clean).

4. Dominio qlan e flusso DNS

Ogni client chiede a Pi-hole. Se il nome è nel dominio locale Pi-hole risponde dai suoi record; altrimenti filtra il nome contro la blocklist e, se non è bloccato, lo chiede a OpenDNS passando dal NAT di pfSense. Unbound su pfSense non conosce qlan: chiedere a .1 un nome locale dà NXDOMAIN, ed è il comportamento atteso.

6. Come si costruisce e si ricrea

La topologia sta una volta sola in pfsense-lab.network_lab (subnet, indirizzi, pool DHCP, dominio, dati per la rete libvirt); i membri dichiarano solo ruolo, gateway_vm e IP. Le identità dei profili tracciati sono generiche (lab/lab); quelle vere vanno in vms/profiles/local.json, insieme al percorso della ISO pfSense (Netgate non pubblica un URL stabile).

vmctl lab plan                 # anteprima: topologia, forward, ordine, XML della rete libvirt
vmctl lab install              # pfsense-lab → pihole-lab → lubuntu22-lab, da dischi vuoti (~30 min); --export consegna poi a libvirt
vmctl lab clean                # ferma e rimuove le tre VM (dischi + artefatti, mai le ISO); rifiuta se il lab è in libvirt
vmctl lab up                   # avvia le tre VM headless in background, in ordine
vmctl lab status · vmctl lab down

vmctl bootstrap-pfsense pfsense-lab          # oppure una VM alla volta
vmctl bootstrap-unattended pihole-lab
vmctl bootstrap-unattended lubuntu22-lab

vmctl clean pihole-lab                        # disco + artefatti (mai le ISO); lab install rifiuta dischi esistenti
vmctl lab attach arch-dms-local --apply       # mette un'altra VM sul segmento (scrive local.json)

pfSense, cosa succede

  1. config.xml renderizzato dalla topologia: interfacce, utenti (bcrypt), Unbound, NAT, regole WAN, forward.
  2. Copia della ISO in artifacts/pfsense-lab/pfsense/install.iso: xorriso estrae rc.local e bsdinstall/script, growisofs -M innesta installerconfig, il nuovo rc.local e lo script patchato (una ricostruzione perderebbe gli extent El Torito nascosti di FreeBSD).
  3. QEMU pc/BIOS, disco bootindex=1, CD IDE bootindex=2, seriale su stdio.
  4. bsdinstall: GPT, pool ZFS su vtbd0, base.txz, /cf/conf/config.xml; poi sync, token ==> pfSense installation complete!, shutdown -p.

Pi-hole e Lubuntu, cosa succede

  1. Autoinstall Ubuntu sulla NIC di fase install (slirp con il forward SSH del profilo), come ogni altro profilo Ubuntu.
  2. Primo avvio in background, attesa SSH, cloud-init e apt.
  3. Hook network_lab: nome dell'interfaccia dal MAC, upload di lan.yaml (+ pihole.toml, liste, password), setup.sh con sudo: installer Pi-hole --unattended, pihole setpassword, netplan statico, cloud-init fuori dalla rete, DHCP FTL, wait-online spento sul client.
  4. Stop. Dal prossimo avvio la stessa NIC è sul segmento con l'indirizzo statico.
Perché è tutto isolato. Il segmento non ha servizi dell'host: senza pfSense acceso i client non escono e senza Pi-hole non risolvono nulla. È voluto: lo scopo è vedere cosa succede quando manca un pezzo, cambiare regole sul firewall o le liste DNS e osservare l'effetto sul client, senza toccare la rete vera dell'host. In più, su QEMU puro non serve alcun privilegio: niente bridge, niente tap.

7. La strada libvirt

vmctl lab export               # lab down, export-libvirt delle tre VM, virsh start in ordine, verifica GUI e SSH sulla LAN
vmctl lab check                # le stesse sonde, in qualunque momento (capisce da solo se il lab è in libvirt o in QEMU)
vmctl lab unexport             # virsh shutdown atteso, unexport-libvirt: si torna a QEMU puro
vmctl lab libvirt-test         # export + check + unexport in un colpo; --keep lo lascia in libvirt

# a mano, se serve:
virsh -c qemu:///system net-list            # lab-lan: bridge virbr-lab, host 192.168.0.254, senza DHCP/DNS
virsh -c qemu:///system start pfsense-lab   # poi pihole-lab, lubuntu22-lab
xdg-open http://192.168.0.1/  ·  http://192.168.0.10/admin/

L'export traduce le NIC di runtime: la WAN slirp diventa la rete libvirt default, il segmento la rete lab-lan, definita e avviata se manca. Disco e NVRAM restano quelli di artifacts/, per percorso assoluto. Non avviare lo stesso disco con QEMU e con libvirt insieme: dopo l'export si usa virsh finché non si fa unexport-libvirt.

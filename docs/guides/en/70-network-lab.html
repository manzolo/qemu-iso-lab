Network lab: pfSense, Pi-hole and Lubuntu

Reproducible lab of manzolo/qemu-iso-lab · profiles pfsense-lab, pihole-lab, lubuntu22-lab · segment lab-lan, domain qlan · kvm-lab's network lab ported to plain QEMU, with the libvirt road through vmctl export-libvirt

Three virtual machines recreate a small company network on an isolated segment: a firewall/router doing NAT towards the Internet, an ad-filtering DNS resolver that also hands out addresses over DHCP, and a desktop client. Everything installs from scratch without interaction (vmctl lab install) and can be destroyed and recreated in half an hour. The difference from kvm-lab is where the host sits: on plain QEMU the segment is a multicast socket between the VMs and the host has no address on the LAN, so it enters from the WAN side of the firewall through port forwards; after the export to libvirt the segment becomes the lab-lan network and the host is .254 again, as before.

2. The three components

pfSense · firewall and gateway · profile pfsense-lab

FreeBSD, pfSense CE 2.7.2, ZFS, BIOS, serial console · scripted bsdinstall, config.xml rendered by vmctl

  • NAT: everything leaving lab-lan is masqueraded with the WAN address taken from QEMU's slirp.
  • LAN rules "allow LAN to any" (IPv4 and IPv6); WAN rules allowing GUI (80) and SSH (22) from the WAN side, i.e. from the host.
  • NAT port forwards: 8081 → Pi-hole :80, 2238 → Pi-hole :22, 2239 → Lubuntu :22.
  • LAN DHCP disabled: Pi-hole does it. Unbound on; system DNS .10.
  • GUI over HTTP at http://127.0.0.1:8080/, users admin and the profile user (same password, bcrypt hash); the project SSH key already in both accounts.

Pi-hole · DNS and DHCP · profile pihole-lab

Ubuntu Server 22.04.5 (autoinstall) + Pi-hole v6 from the official installer with a pre-seeded pihole.toml

  • Resolver for the whole LAN with the StevenBlack blocklist.
  • Upstreams OpenDNS 208.67.222.222 and .220.220, reached through pfSense.
  • Generated local records: the router and every lab member (firewall.qlan, pi-hole.qlan, lubuntu.qlan), plus those in network_lab.hosts; CNAME pfsense.qlan.
  • DHCP for guests: pool .150–.199, 24 h leases, gateway .1, DNS .10, domain qlan.
  • GUI at http://127.0.0.1:8081/admin/ (through the router), password network_lab.password.

Lubuntu · client · profile lubuntu22-lab

Ubuntu Server 22.04.5 + lubuntu-desktop, LXQt, SDDM autologin

  • Static IP .100, gateway .1, DNS .10: the user workstation.
  • NIC matched by MAC in netplan (match + set-name), same slot and MAC in the install and runtime phases.
  • The host's shared/ folder on /mnt/shared (virtiofs), links ~/shared and on the desktop.
  • systemd-networkd-wait-online disabled: with the NetworkManager renderer it stalled every boot for 120 s.

Host · where you drive from

plain QEMU: 127.0.0.1 + forwards · libvirt: 192.168.0.254 on the virbr-lab bridge

  • vmctl lab up/down/status/check, vmctl shell <vm>, vmctl console <vm> for the serial, vmctl attach <vm> for the screen.
  • The forwards live in the router profile (networks[].hostfwd) and in the NAT rules of the config.xml: vmctl lab plan checks they agree.
  • After vmctl lab export the host sits on the LAN and everything is reachable at the real IPs.

Ports 2238 and 2239 are the members' own ssh_host_port: during the install they are a slirp forward on the VM itself, afterwards a forward on the router. vmctl shell does not change.

4. Domain qlan and DNS flow

Every client asks Pi-hole. If the name is in the local domain Pi-hole answers from its records; otherwise it filters the name against the blocklist and, if not blocked, asks OpenDNS through pfSense's NAT. Unbound on pfSense does not know qlan: asking .1 for a local name gives NXDOMAIN, and that is the expected behaviour.

6. How it is built and rebuilt

The topology lives once, in pfsense-lab.network_lab (subnet, addresses, DHCP pool, domain, data for the libvirt network); the members declare only role, gateway_vm and IP. The identities of the tracked profiles are generic (lab/lab); the real ones go in vms/profiles/local.json, together with the path of the pfSense ISO (Netgate publishes no stable URL).

vmctl lab plan                 # preview: topology, forwards, order, libvirt network XML
vmctl lab install              # pfsense-lab → pihole-lab → lubuntu22-lab, from empty disks (~30 min); --export then hands it to libvirt
vmctl lab clean                # stop and remove the three VMs (disks + artifacts, never the ISOs); refuses while the lab is in libvirt
vmctl lab up                   # start the three VMs headless in the background, in order
vmctl lab status · vmctl lab check · vmctl lab down

vmctl bootstrap-pfsense pfsense-lab          # or one VM at a time
vmctl bootstrap-unattended pihole-lab
vmctl bootstrap-unattended lubuntu22-lab

vmctl clean pihole-lab                        # disk + artifacts (never the ISOs); lab install refuses existing disks
vmctl lab attach arch-dms-local --apply       # puts another VM on the segment (writes local.json)

pfSense, what happens

  1. config.xml rendered from the topology: interfaces, users (bcrypt), Unbound, NAT, WAN rules, forwards.
  2. Copy of the ISO into artifacts/pfsense-lab/pfsense/install.iso: xorriso extracts rc.local and bsdinstall/script, growisofs -M grafts installerconfig, the new rc.local and the patched script (a rebuild would lose FreeBSD's hidden El Torito extents).
  3. QEMU pc/BIOS, disk bootindex=1, IDE CD bootindex=2, serial on stdio.
  4. bsdinstall: GPT, ZFS pool on vtbd0, base.txz, /cf/conf/config.xml; then sync, token ==> pfSense installation complete!, shutdown -p.

Pi-hole and Lubuntu, what happens

  1. Ubuntu autoinstall on the install-phase NIC (slirp with the profile's SSH forward), like every other Ubuntu profile.
  2. First boot in the background, wait for SSH, cloud-init and apt.
  3. network_lab hook: interface name from the MAC, upload of lan.yaml (+ pihole.toml, lists, password), setup.sh with sudo: Pi-hole installer --unattended, pihole setpassword, static netplan, cloud-init out of the network, FTL DHCP, wait-online off on the client.
  4. Stop. From the next boot the same NIC is on the segment with the static address.
Why everything is isolated. The segment has no host services: without pfSense up the clients do not get out and without Pi-hole they resolve nothing. It is deliberate: the point is to see what happens when a piece is missing, to change firewall rules or DNS lists and watch the effect on the client, without touching the host's real network. And on plain QEMU no privilege is needed: no bridge, no tap.

7. The libvirt road

vmctl lab export               # lab down, export-libvirt of the three VMs, virsh start in order, GUI and SSH checks on the LAN
vmctl lab check                # the same probes, any time (it detects by itself whether the lab is in libvirt or in QEMU)
vmctl lab unexport             # waited virsh shutdown, unexport-libvirt: back to plain QEMU
vmctl lab libvirt-test         # export + check + unexport in one go; --keep leaves it in libvirt

# by hand, if needed:
virsh -c qemu:///system net-list            # lab-lan: bridge virbr-lab, host 192.168.0.254, no DHCP/DNS
virsh -c qemu:///system start pfsense-lab   # then pihole-lab, lubuntu22-lab
xdg-open http://192.168.0.1/  ·  http://192.168.0.10/admin/

The export translates the runtime NICs: the slirp WAN becomes the libvirt default network, the segment the lab-lan network, defined and started when missing. Disk and NVRAM stay the ones in artifacts/, by absolute path. Never run the same disk in QEMU and libvirt at the same time: after the export use virsh until you unexport-libvirt.
